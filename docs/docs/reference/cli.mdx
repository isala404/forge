# CLI Reference

## Project Root Discovery

`forge check`, `forge generate`, `forge migrate`, and `forge test` walk up from the current directory until they find a `forge.toml`, mirroring how `cargo` and `git` behave. You can run them from `frontend/`, `migrations/`, or any nested subdirectory and they will resolve the project root for you. The resolved root is printed once at the start of each command. If no `forge.toml` is found before hitting the filesystem root, the command exits with an error.

## forge new

Two modes:

### 1. Scaffold a new project

```bash
forge new [project-name] --template <id> [options]
```

| Option               | Description                                                      |
| -------------------- | ---------------------------------------------------------------- |
| `--template <id>`    | Required template id copied from the embedded example catalog    |
| `--output, -o <dir>` | Output directory (defaults to project name)                      |
| `--no-lock`          | Skip generating `Cargo.lock` before the initial commit           |
| `--yes, -y`          | Accept all prompts non-interactively (skips confirmations during project creation) |

### 2. Scaffold a handler in an existing project

```bash
forge new <kind> <name>
```

`<kind>` is one of `query`, `mutation`, `job`, `cron`, `workflow`, `daemon`, `webhook`, `mcp_tool`, `model`, `enum`. Writes a new file under `src/functions/<name>.rs` (or `src/schema/<name>.rs` for `model`/`enum`), appends `pub mod <name>;` to the appropriate `mod.rs`, and inserts `mod functions;` into `src/main.rs` if missing. The generated file includes a top-of-file Context API reference and sensible per-kind defaults you can edit. Walks up to find `forge.toml`, so you can run it from any subdirectory.

```bash
forge new query list_invoices
forge new mutation create_invoice
forge new model Invoice
```

Supported template ids:

```bash
with-svelte/minimal
with-svelte/demo
with-svelte/realtime-todo-list
with-dioxus/minimal
with-dioxus/demo
with-dioxus/realtime-todo-list
```

```bash
# Small Svelte starter
forge new my-app --template with-svelte/minimal

# Real-time Dioxus example
forge new my-app --template with-dioxus/realtime-todo-list

# Custom output directory
forge new my-app --template with-svelte/demo --output /path/to/projects/my-app
```

### Post-Scaffold Automation

After scaffolding the project directory, `forge new` automatically:

1. Installs frontend dependencies (`bun install`)
2. Runs `forge generate` to produce frontend bindings
3. Runs `cargo fmt` and `bun run format` to normalize code style
4. Generates `Cargo.lock` (optional, skipped with `--no-lock`)
5. Runs the skill installer if applicable
6. Runs `git init` and creates an initial commit

If a step's binary is not installed (e.g., `bun` is missing), the command prints a warning and continues. The project is still fully usable.

## Development Environment

Start your development environment with Docker Compose:

```bash
# Start development environment
docker compose up --build

# Stop containers
docker compose down

# Stop and remove volumes
docker compose down -v
```

### Requirements

| Tool   | Minimum Version       |
| ------ | --------------------- |
| Docker | 24+ (with Compose v2) |

### Services

When running, the following services are available:

| Service  | URL                   |
| -------- | --------------------- |
| Frontend | http://localhost:9080 |
| Backend  | http://localhost:9081 |

PostgreSQL runs inside the Docker network and is not exposed to the host. The backend connects to it via the internal `db` hostname. To access the database directly, use `docker compose exec`:

```bash
docker compose exec db psql -U postgres -d my-app
docker compose exec db psql -U postgres -d my-app -c "SELECT * FROM users LIMIT 5"
```

### Watch Scope

The backend container uses cargo-watch with an `.ignore` file (deny-all `*` with allowlist). Only these paths trigger backend restarts:

- `src/`
- `migrations/`
- `build.rs`
- `Cargo.toml`
- `Cargo.lock`
- `.env`
- `forge.toml`

## forge test

Run backend unit tests and frontend Playwright tests.

```bash
forge test [options] [-- test-args...]
```

| Option            | Description                            |
| ----------------- | -------------------------------------- |
| `--skip-backend`  | Skip Rust backend unit tests           |
| `--skip-frontend` | Skip Playwright frontend tests         |
| `--ui`            | Run Playwright in interactive UI mode  |
| `--headed`        | Run in a visible browser window        |

Trailing arguments after `--` are forwarded to the Playwright test runner.

### How it works

`forge test` runs a fully self-contained test cycle — no running dev server or docker compose needed:

1. Builds the project with the `embedded-frontend` feature (frontend compiled in)
2. Starts a PostgreSQL container on a random port
3. Starts the built binary on a random port
4. Waits up to 120 seconds for `/_api/health` to return healthy
5. Runs the Playwright suite against that server
6. Stops the binary and removes the PG container

Docker must be available for frontend tests. If you already have a server running (e.g. in CI), set `FORGE_TEST_URL` to skip the build/start steps entirely.

### FORGE_TEST_URL

```bash
FORGE_TEST_URL=http://localhost:9081 forge test --skip-backend
```

When `FORGE_TEST_URL` is set, `forge test` skips the build, PG container, and binary start — it just checks that the URL is reachable and runs Playwright against it.

### Playwright Browser Install

Playwright browser binaries are installed automatically on first run if missing.

```bash
# Run all tests
forge test

# Backend unit tests only
forge test --skip-frontend

# Frontend only, visible browser
forge test --skip-backend --headed

# Pass args through to Playwright
forge test -- --test my_specific_test
```

## forge check

Validate project configuration and dependencies.

```bash
forge check [options]
```

| Option                | Description                                                                                              |
| --------------------- | -------------------------------------------------------------------------------------------------------- |
| `--config, -c <path>` | Path to forge.toml (default: ./forge.toml)                                                               |
| `--no-prepare`        | Skip the auto-refresh of `.sqlx/`. Treats a stale cache as a real failure (use this in CI)               |
| `--prepare-only`      | Run the `.sqlx/` auto-refresh and exit. Useful when you want the refresh side-effect without the rest    |

### Auto-Refresh of `.sqlx/`

`forge check` hashes source mtimes under `src/` against the `.sqlx/` cache and runs `cargo sqlx prepare --workspace` automatically when sources are newer. This eliminates the "edit SQL → check → cache-miss errors → prepare → check again" loop.

Requires `cargo-sqlx` and a reachable `DATABASE_URL` (resolved from the env var first, then `forge.toml [database].url`). If either is missing, the refresh fails with an actionable hint and the rest of the check still runs.

### Checks Performed

- forge.toml validity and required sections
- Cargo.toml and forge dependency
- Directory structure (src/, src/schema/, src/functions/, migrations/)
- Migration file naming and `-- @up` markers
- Function files with forge macros (query, mutation, job, cron, workflow, daemon, webhook, mcp_tool)
- Schema files with `#[forge::model]` or standard derives (`Serialize`, `FromRow`)

- SQLx offline cache freshness (warns if `.sqlx/` is stale relative to migration files)
- `sqlx.toml` presence and `offline = true` validation
- Generated bindings staleness (diffs current bindings against freshly generated output)
- Dioxus-specific checks (`frontend/Dioxus.toml` presence, `rustfmt` on frontend `.rs` files)
- Rust linting (cargo fmt, clippy)
- Frontend configuration (if present)
- Frontend linting (ESLint, Prettier)

```bash
# Full project check
forge check

# Custom config location
forge check --config ./config/forge.toml
```

## forge generate

Generate frontend/runtime bindings from backend source code.

`forge generate` is a **manual step** — it is not wired into `cargo build`. Run it after any change to handler signatures, argument types, return types, models, or enums. `forge check` reports staleness if you forget.

```bash
forge generate [options]
```

| Option                 | Description                                             |
| ---------------------- | ------------------------------------------------------- |
| `--force`              | Force regeneration even if files exist                  |
| `--output, -o <dir>`   | Output directory (defaults to the detected target path) |
| `--target <framework>` | Frontend target (`sveltekit` or `dioxus`). Defaults to SvelteKit when no framework is auto-detected |
| `--src, -s <dir>`      | Source directory to scan (default: src)                 |
| `--yes, -y`            | Auto-accept prompts (useful for CI)                     |

### Generated Files

SvelteKit target:

| File               | Description                                                      |
| ------------------ | ---------------------------------------------------------------- |
| types.ts           | TypeScript interfaces from Rust models and input DTOs            |
| api.ts             | Function bindings for queries, mutations, jobs, and workflows    |
| stores.ts          | Svelte store exports                                             |
| runes.svelte.ts    | Svelte 5 runes helpers                                           |
| reactive.svelte.ts | Generated when queries exist; runes-based subscription functions |
| auth.svelte.ts     | Generated when auth is configured                                |
| index.ts           | Re-exports all modules                                           |

Dioxus target:

| File     | Description                                                       |
| -------- | ----------------------------------------------------------------- |
| types.rs | Rust types generated from models and input DTOs                   |
| api.rs   | Typed RPC functions and hooks                                     |
| mod.rs   | Re-exports of generated modules plus `forge-dioxus` runtime items |

Backend handler/model files are authored in `src/functions/` and `src/schema/`. `forge generate` then syncs generated frontend/runtime artifacts from that backend source of truth.

```bash
# Generate bindings for the detected target
forge generate

# Generate Dioxus bindings explicitly
forge generate --target dioxus

# Force regenerate everything
forge generate --force

# CI mode (no prompts)
forge generate -y

# Custom directories
forge generate --src ./backend/src --output ./web/src/lib/forge
```

## forge migrate

Manage database migrations.

```bash
forge migrate [action] [options]
```

| Option                       | Description                                   |
| ---------------------------- | --------------------------------------------- |
| `--config, -c <path>`        | Configuration file path (default: forge.toml) |
| `--migrations-dir, -m <dir>` | Migrations directory (default: migrations)    |

### Actions

| Action    | Description                                                     |
| --------- | --------------------------------------------------------------- |
| `up`      | Run all pending migrations                                      |
| `status`  | Show migration status                                           |
| `prepare` | Run pending migrations, then refresh the `.sqlx/` offline cache. Requires `cargo-sqlx` (`cargo install sqlx-cli --locked`); prints install instructions if missing |

Forward-only — migrations don't have a rollback path. To undo something, write a new migration that reverses it.

### Automatic migrations

During development, migrations run automatically when the backend starts. Pending migrations are applied before the server accepts requests, so you don't need to run `forge migrate up` manually.

### Manual migration management

Since PostgreSQL is only accessible inside the Docker network, use `docker compose exec` to run migration commands or interact with the database directly:

```bash
docker compose exec db psql -U postgres -d my-app -c "SELECT * FROM forge_system_migrations ORDER BY applied_at"
docker compose exec backend forge migrate status
docker compose exec backend forge migrate prepare
docker compose exec db psql -U postgres -d my-app
```

For production or CI, `forge migrate` connects via `DATABASE_URL` directly:

```bash
forge migrate up
forge migrate status
forge migrate up --config ./config/forge.toml --migrations-dir ./db/migrations
```

### Migration File Format

Migration files must be named `NNNN_name.sql` (e.g., `0001_initial.sql`). The optional `-- @up` marker is stripped if present, otherwise the entire file is treated as the upgrade SQL.

```sql
CREATE TABLE users (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    email TEXT UNIQUE NOT NULL,
    created_at TIMESTAMPTZ DEFAULT now()
);
```

## forge env

Print shell-init snippets for Forge dev. Add `eval "$(forge env)"` to your shell rc file (`~/.zshrc`, `~/.bashrc`) or `eval (forge env)` for Fish (`~/.config/fish/config.fish`).

```bash
forge env [--shell bash|zsh|fish] [--no-completions]
```

Output:

- `export SQLX_OFFLINE=true` (or the Fish equivalent), so raw `cargo check` does not validate against your live DB
- `export FORGE_ROOT=<resolved project root>` when run inside a project
- Shell completion bindings via `clap_complete`, unless `--no-completions` is set

The shell is auto-detected from `$SHELL`. Pass `--shell` to override.

## forge doctor

One-shot environment check. Verifies your dev environment is set up correctly and prints a remediation hint for anything that fails.

```bash
forge doctor
```

Checks performed:

- Rust toolchain meets the workspace `rust-version` requirement
- `cargo-sqlx` is installed
- `SQLX_OFFLINE=true` is exported
- `DATABASE_URL` is set, parseable, and reachable on a TCP probe (1s timeout)
- Docker daemon is reachable when `docker-compose.yml` exists at the project root
- `bun` is available when `frontend/package.json` exists; `dx` (dioxus-cli) when `frontend/Cargo.toml` exists
- `forge.toml` parses cleanly (when run inside a project)
- `.sqlx/` cache is fresher than the newest `src/**/*.rs` file
- The most recent migration file is non-empty

Each result is one line, prefixed with `[OK]`, `[!]`, `[X]`, or `[i]`. The command exits non-zero if any check fails.

## Cargo Features

`forgex` defaults to `full`, which enables everything. Use `default-features = false` plus one of the presets (or individual subsystem flags) to produce a smaller binary.

```toml
# Cargo.toml — slim worker binary, no HTTP stack
forgex = { version = "0.10.1", default-features = false, features = ["worker"] }
```

### Preset bundles

| Feature | Includes | Description |
| ------- | -------- | ----------- |
| `full` | all subsystems | Default. Equivalent to today's behavior; existing apps need no changes. |
| `worker` | `jobs`, `workflows`, `cron`, `daemons`, `otel` | Background workers without an HTTP surface. Use for binaries that consume jobs/workflows but serve no traffic. |
| `api` | `gateway`, `otel` | HTTP gateway with observability, no background workers. Use for read-heavy API nodes. |
| `minimal` | `gateway` | Smallest possible HTTP binary. Structured logs go to stderr only; no OTel exporters. |

### Subsystem features

| Feature | Default | Description |
| ------- | ------- | ----------- |
| `gateway` | yes | Axum HTTP server: RPC, SSE realtime, OAuth, MCP, webhooks, signals, TLS termination. Pulls the full axum/tower stack. Disable for worker-only binaries. |
| `jobs` | yes | PostgreSQL-backed job queue with `SKIP LOCKED` worker. |
| `workflows` | yes | Versioned durable workflow executor with signature guards and compensation. |
| `cron` | yes | Cron scheduler with leader-only execution and exactly-once guarantees. |
| `daemons` | yes | Long-running daemon runner (leader-elected or per-node). |
| `mcp-oauth` | yes | OAuth 2.1 + PKCE authentication for MCP tools. Requires `gateway`. Without it, MCP uses JWT bearer auth only. |
| `geoip` | yes | Bundles a ~10 MB IP-to-country database for signals enrichment. Requires a network fetch at compile time. Omit for offline builds or when you don't use signals. Requires `gateway`. |
| `otel` | yes | OpenTelemetry trace, metric, and log exporters via OTLP HTTP. Pulls ~5 OTel crates plus protobuf stubs. Disable to skip those deps entirely. |

### Other features

| Feature | Default | Description |
| ------- | ------- | ----------- |
| `testcontainers` | no | Enables `TestQueryContext`, `TestMutationContext`, and friends that spin up a real PostgreSQL container. Enable in dev/CI integration test binaries only — not in production. |
| `embedded-frontend` | no | Embeds the compiled frontend bundle into the binary at build time (`rust-embed`). Used by `forge test` to produce a self-contained test binary. Enable explicitly when you want a single-binary deployment. |
